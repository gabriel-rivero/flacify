# v0.4 plan — streaming and the segmented cache

Status: working plan, 2026-11-17. Supersedes the v0.4 sketch in
[`roadmap.md`](roadmap.md#v04--streaming-and-cache-polish), which stays as the summary.

Exit criteria are unchanged: a 60-minute track, zero dropouts, seek to 55:00 works, and a
second play costs 0 s of GPU time. What follows is how, in the order the work can land.

## What v0.4 has to fix

The v0.3 player assumes the whole track is in RAM twice: the decoded source and the
generated audio. A 60-minute track is 1.38 GB per copy, so the design caps at roughly five
minutes. Three things follow from that.

| problem | today | v0.4 |
|---|---|---|
| memory | whole-track source + whole-track render + every frontier chunk retained | one source segment and two rendered segments resident, about 33 MB |
| seek | an index into full-length buffers | a segment read; uncached regions play passthrough |
| second play | re-renders, or reads a 69 MB float WAV per 3 minutes | reads FLAC segments, 0 s of GPU |

## The three risks, and what testing them turned up (2026-11-17)

### 1. FLAC writing: solved, no fork

`flacenc` 0.5.1 has the defect already recorded in `cache.rs:14`. This is the root cause,
measured on a 3 s 24-bit stereo file:

- Unpatched, symphonia 0.5.5 **cannot probe** the file (`IoError: end of stream`), while
  claxon 0.4.3 decodes both channels bit-exactly and libFLAC's `flac -t` warns "sample or
  frame number does not increase correctly". So the defect is not in the channel data.
- `STREAMINFO` advertises `min_blocksize = 640` (the short last frame) next to
  `max_blocksize = 4096`, while every frame header carries the fixed-blocking-strategy
  bit. A reader that sees min ≠ max treats the stream as variable-blocksize, expects
  sample numbers, and misreads. libFLAC writes min = max = the block size in this case,
  which is why its files read everywhere.
- `flacenc` already intends that (`coding.rs:666` calls `set_block_sizes(bs, bs)`) but
  `Stream::add_frame` recomputes the minimum from the actual frames afterwards.
- **Fix, public API only:** after `encode_with_fixed_block_size`, call
  `stream.stream_info_mut().set_block_sizes(BLOCK, BLOCK)` before `Stream::write`.
  Result: symphonia probes, 144000/144000 frames, L and R `max_abs = 0.0` against the
  24-bit reference, claxon identical, `flac -t` clean. No fork, no byte surgery.

### 2. Bit-identical segmented rendering: needs an API, then a test

The output is not a pure function of a frame range. Four things carry across a segment
boundary:

- **Window lattice.** A render must start at a multiple of `step` (197 760), not `window`.
- **Seed.** `window_seed` hashes a track-level seed with the absolute window index
  (`pipeline.rs:186`), so a segment starts with `windows = segment_start / step`.
- **Tail.** The first `overlap` output samples of a window are the previous window's
  generated tail. A segment that starts cold must render one extra window and keep its
  tail, or persist the tail.
- **Gain.** Loudness gain is fixed from the first block of window 0 and applied to the
  whole track, so a segment rendered alone cannot recompute it. It has to be persisted in
  the manifest, and segment 0 renders first.

The first three are a `core` change: `Pipeline::start_at(window_index)` plus a carry-in
and carry-out for the tail. The acceptance test is the point of the whole release: a
render of `[0, n)` in 1-, 7- and 13-step slices must equal a single whole-track render
sample for sample, including the last-segment path.

### 3. Chunked decode and resample: overlap-save works

`Resampler::process` (`crates/core/src/dsp/resample.rs:80`) is a pure function with
zero-padded edges, and 44.1 → 48 kHz is 147/160 after the GCD, so `half_len = 10 × 160 =
1600` input samples (33 ms). Feeding a chunk with 1600 samples of pre-roll and discarding
the affected output samples gives an exact interior. That is the mechanism the source
pass uses; a test pins chunked output to whole-buffer output.

## Decisions

| # | decision | why, and what it rules out |
|---|---|---|
| D1 | **A source tier per track.** One sequential decode+resample pass writes the 48 kHz stereo source as FLAC 24-bit, next to the rendered segments. | Both A/B sides then read from files at the same clock, so the toggle stays sample-locked, MP3 seek warm-up cannot drift it, and the renderer gets random access. Costs about 0.55 GB per hour of audio, inside the cap. |
| D2 | **Segments are 7 steps, 1 384 320 frames, 28.84 s** — not 30 s. | A segment start must be a `step` multiple or the crossfade lattice shifts. 7 steps is the closest to the architecture's 30 s. |
| D3 | **Cache key = blake3 of the source file bytes** (+ weights hash + pipeline version + window/overlap + splice), as `architecture.md:280` already says. | Drops a full decode from every cache lookup, which today hashes the whole decoded buffer. A retagged file misses; that is the cost and it is the documented contract. |
| D4 | **Segments are FLAC 24-bit.** | Measured on 28.84 s of pink noise, which is the worst case for any lossless codec: 24-bit WAV is 8.31 MB, `flacenc` writes 6.16 MB, libFLAC would write 3.44 MB. Music compresses better than noise, so the real ratio is between those; the acceptance run measures it. −144 dBFS quantisation is below the noise floor of anything the model generates, so a cache hit differs from a fresh render by at most one 24-bit LSB. libFLAC through a C binding stays the fallback if disk turns out to matter, and `flacenc` stays the default because it needs no C toolchain on three platforms. |
| D5 | **Rendered segments are written whole and renamed into place**; the manifest is updated after each segment with `fsync`. | A kill leaves playable segments plus a manifest that names them; a segment that is not in the manifest is adopted if it parses, deleted if it does not. |
| D6 | **The scheduler renders segment 0 first and then follows the playhead**, not strictly in order. | The gain comes from window 0, so segment 0 is a prerequisite for every other segment. After it, seek can prioritise. |
| D7 | **The player keeps three segments: current, next, previous.** Decoded by a reader thread, swapped in with `ArcSwap`, never in the audio callback. | 33 MB resident for a 60-minute track, and the callback still does no allocation or locks. |
| D8 | **Readiness is a segment bitmap, not a monotonic counter.** | Out-of-order fill is the point of D6; `Frontier::publish`'s in-order assumption has to go. |
| D9 | **LRU with a 20 GB default cap**, never the open entry, manifest always kept, usage shown by `flacify diagnose`. | Matches `architecture.md:289`; also the only thing that clears the v5 leftover entries. |

## Work, in dependency order

Landed 2026-11-17: V4-1, V4-2, V4-3's storage format with V4-4 folded in (the FLAC
writer and its regression test shipped together as `enhance -o x.flac`), V4-5's key
(D3, `CACHE_VERSION` 8), its streaming decoder and the source tier itself. Everything
else is queued.

Each item is one PR: the code, a test that fails without it, and the doc line that would
have been wrong. Items in the same wave touch different files and can run in parallel.

## Not in v0.4

Real-time mode, live capture, the system sink, batch folders, signing: all deferred, see
the roadmap's [Not on the roadmap](roadmap.md#not-on-the-roadmap) section. `--splice` stays
off; the low-band work is parked on the model's phase, not on anything here.

## Open questions that only the acceptance run can answer

1. Does the renderer keep up on the 4060 Ti box when a seek asks it to jump ahead? RTF
   0.66 leaves less headroom than 0.54.
2. Whether the source tier should be evicted separately from the render (it is half the
   entry and can be rebuilt, so it is the natural first victim under pressure).
3. Whether the 24-bit cache is audible at all on the A/B switch, measured rather than
   argued.
4. What the source tier costs a full-band file. Every load through `Session` writes the
   tier before the analysis runs, so a file that then plays passthrough untouched pays
   about 0.55 GB of disk per hour and a cold pass of roughly 0.09 s per 20 s of audio
   (measured on 44.1 kHz stereo) for a second play the tier never serves. The measured
   entry was 2.9 MB per 20 s of noise-like audio, and a full-band load now also fails
   where the cache directory cannot be created. Measure the cold-load cost and the entry
   size on the acceptance track both ways, then decide whether a full-band load may skip
   the tier; `flacify probe` already does.
